Simfolio — Go live

Path A, in depth

Client on Cloudflare Pages, server on Render, Postgres on Neon. Three free accounts, no code rewritten. Read the whole thing once before you start clicking — the order matters, and each service needs a value the previous one produced.

Part 0 — Before you touch a dashboard

Four accounts, all free, all sign-up-with-email. Get them first; every later step asks for something one of them gave you.

Account What you copy out of it
GitHubNothing to copy — but your code has to live there. See the next section.
FinnhubAPI key — live quotes, search, the US + Canadian symbol universe
Twelve DataAPI key — the price history behind every chart
Neon + Render + CloudflareThe three hosts below. Sign in with GitHub for all three.
Without the two API keys Simfolio still runs — it falls back to simulated prices, and everything else works identically. With them you get real quotes. That fallback is a design choice, not a bug: it is why the app boots on a laptop with no configuration at all.

The shape of it

On your laptop all three pieces live in one place and find each other over localhost. Deployed, they sit on three different companies' computers and find each other over the public internet by hostname. That's the entire difference. Same code, longer wires.

Browser
Someone's phone or laptop, anywhere
↓ downloads HTML
Cloudflare Pages
Your client files. Hands out HTML, CSS, JS. Holds no data, runs no logic.
↓ HTTPS / JSON
Render
Your Express server. Checks passwords, calls Finnhub, executes orders.
↓ SQL over TLS
Neon
Postgres. The only piece that remembers anything.

Note what doesn't happen: the browser never touches the database. It couldn't — the database password lives only on Render, and a browser can't be trusted with it. Every read and write goes through your server, which is exactly why the server exists.

Why three companies instead of one? Because these are three genuinely different jobs. Serving static files wants a global CDN. Running Node wants a long-lived process. Storing data wants durable disk and backups. Platforms that do all three exist, but they're worse at each. Splitting them is normal and it's what the job looks like.

Concept: environment variables

You already met these in your .env file. Understand them properly now, because deployment is mostly just setting them.

An environment variable is a named value the operating system hands your program when it starts. Your code reads it instead of hard-coding the value:

const url = process.env.DATABASE_URL;   // not a hard-coded connection string

This is what lets the identical code run in two places with different behaviour. On your laptop the values come from .env. On Render you type them into a form in their dashboard and Render injects them. The .env file itself is never uploaded — it's in .gitignore, and if you ever commit one, treat every secret in it as burned and rotate them.

In your project, server/src/config/loadConfig.js is the single file that reads these. Everything else receives values. That's the pattern — one door in.

Push to GitHub before anything else

Render and Cloudflare both deploy by watching a Git repository. You push a commit; they notice and rebuild. There's no "upload my folder" button worth using — GitHub is the delivery mechanism, not a formality.

Before pushing, confirm .gitignore lists node_modules, .env, and data/. Then check what you're about to send with git status and actually read the list. A committed .env means every secret in it is burned.

Part 1 — Neon: the database

Do this first, because Render needs its connection string.

01
Sign up at neon.tech. Create a project; name the database simfolio. Pick the region closest to where you'll put the server — every query pays that round trip.
02
Copy the connection string it shows you. It looks like the line below. This single string is host, port, user, password and database name in one — and it is a password. Never commit it, never paste it in a screenshot.
postgres://alex:AbC123xyz@ep-quiet-moon-12345.us-east-2.aws.neon.tech/simfolio?sslmode=require
03
Create the tables in it. Your new Neon database is completely empty — migrations you ran locally built tables in your local SQLite file and know nothing about this one. Run them against Neon from your laptop, once:
$ cd server
$ DATABASE_URL="postgres://...your-neon-string..." PG_SSL=true npm run migrate

Putting the variable before the command sets it for that one command only — your .env is untouched, so your local SQLite setup keeps working. On Windows PowerShell it's $env:DATABASE_URL="..." on its own line first. This is the moment your code path switches: with DATABASE_URL set, the container loads the Postgres repositories instead of the SQLite ones — same interfaces, different adapter.

Skip npm run seed here unless you want the demo account public. Real signups will create real rows.

Part 2 — Render: the server

Render runs your Express app as a long-lived process, which is exactly what it needs (and exactly what Cloudflare Workers can't give it).

01
At render.com, New → Web Service, connect your GitHub repo.
02
Set Root Directory to server. This is the step people miss — your repo has the client at the top level, and without this Render looks for package.json in the wrong folder and fails immediately.
03
Build command npm install, start command npm start. Build runs once per deploy; start is the process that keeps running. Use npm start, not npm run dev — dev restarts on file changes, which is meaningless and wasteful in production.
04
Add the environment variables:
variable value
DATABASE_URLYour Neon string from Part 1
PG_SSLtrue — Neon refuses unencrypted connections
JWT_SECRETA new long random string — not the one from your laptop
FINNHUB_API_KEYSame key as local
TWELVEDATA_API_KEYSame key as local
NODE_ENVproduction
CORS_ORIGINLeave blank for now — you don't have the Pages URL yet. You'll come back.

Don't set PORT. Render assigns one and passes it in; your code already reads it.

05
Deploy, then watch the log stream. It's the same output you saw in your terminal. When it reaches "listening", open https://your-service.onrender.com/health and confirm you get JSON back. Do not move on until you do.

Part 3 — Cloudflare Pages: the client

01
Point the client at Render first. Right now it's hard-coded to your laptop. In Simfolio.dc.html the apiBaseUrl prop defaults to http://localhost:4000 — change that default and the fallback beside it to your Render URL, and change DEFAULT_BASE_URL in src/gateways/resolveGateway.js to match. Commit and push.
02
In the Cloudflare dashboard: Workers & Pages → Create → Pages → connect your repo. Build command: leave empty. Build output directory: /. There's genuinely nothing to compile — that's the upside of no bundler.
03
Deploy. You get a URL like simfolio.pages.dev.
04
Go back to Render and set CORS_ORIGIN to that exact URL — https://simfolio.pages.dev, https, no trailing slash. Render restarts. Now the circle is closed.

Concept: CORS, since it will bite you

Browsers enforce a rule: JavaScript loaded from one domain may not read responses from a different domain unless that other domain explicitly permits it. It's what stops a malicious page from quietly calling your bank's API using your logged-in session.

Locally you never noticed, because client and server were both localhost. Deployed they're on different domains, so your server has to say "requests from simfolio.pages.dev are fine" — which is precisely what CORS_ORIGIN does.

The symptom is unmistakable once you've seen it: the app loads and looks fine, every request fails, and the browser console says something about blocked by CORS policy. Nine times in ten the fix is a typo in CORS_ORIGIN — http instead of https, or a trailing slash. Resist setting it to *; you'd be turning off the protection rather than configuring it.

Verify in order

Check each link in the chain separately, nearest to the data first. When something's broken this tells you which of the three services to look at, instead of guessing.

01
Neon's dashboard lists a users table. → migrations landed. (You will see eight in total — the five that hold your data, plus symbols, app_meta and the migration runner's own bookkeeping table.)
02
/health on the Render URL returns JSON. → server is up and reached its database.
03
The Pages URL loads and looks right. → client deployed.
04
Sign up on the live site. → client reached server, server wrote to Postgres, CORS is right. This one test covers the whole chain.
05
Buy something, then open the site on your phone and log in. Your holdings are there. → that's real persistence on a real database, and the moment the whole thing stops feeling theoretical.

What free tiers actually cost you

Service The catch
RenderSleeps after ~15 minutes idle. The next visitor waits up to 50 seconds for a cold start. Put a line in your README so reviewers don't think it's broken.
NeonAlso suspends when idle, but wakes in a second or two. Storage limit is far beyond anything you'll hit.
Cloudflare PagesEffectively no catch. Static files, unlimited bandwidth, always warm.
Finnhub / Twelve DataRate limits are now shared across all your visitors, not just you. Your server's quote cache is what makes this survivable.

Two things to fix once it's live

The live price stream. Your server holds one WebSocket to Finnhub and fans it out. Render's free tier runs a single instance, so this works — but it will not survive scaling to two, because each instance would open its own upstream socket and hold its own subscriber list. That's the Redis note in docs/STACK.md, and it's a real answer to have ready if an interviewer asks how you'd scale this.

Tokens in localStorage. Fine for a portfolio project, and worth knowing why it isn't fine in general: any script running on your page can read localStorage, so an XSS bug becomes a stolen session. The production answer is a refresh token in an httpOnly cookie. Being able to explain that trade-off is worth more than having silently done it.

Every deploy from here is git push. Both platforms watch the repo and rebuild on their own. If a deploy breaks the site, the fastest fix is always to roll back to the previous deploy in the dashboard, then debug locally — never debug in production while it's down.
