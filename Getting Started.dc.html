Simfolio — Setup Guide

Getting this running on your computer

Written for someone who has used Python, Java, HTML and CSS, and has never touched a terminal-run server or a database. Do the steps in order. Do not skip step 1.

Time needed
45–90 minutes
Most of it is waiting for installs and signing up for two free accounts.
What you'll end up with
A working app at localhost
Real stock prices, a login, a portfolio that survives a refresh.

First: the mental model

Right now you probably think of "a website" as one thing. This project is actually three separate things that talk to each other. Everything in this guide makes more sense once you can name them.

1
The client (front end)
The HTML/CSS you already understand — Simfolio.dc.html plus the src/ folder. It draws buttons and charts. It knows nothing about stock prices or passwords; it asks for them.
2
The server (back end)
The server/ folder. A program written in JavaScript that sits running and waits to be asked questions: "who is this user?", "what does AAPL cost?", "buy 3 shares". It is exactly like a Python script that never exits — a while True: loop listening on a port.
3
The database
A single file on your disk that remembers things after the server stops. Users, holdings, transactions. Without it, closing the terminal would erase every account.
The one sentence to remember: the browser talks to the server over HTTP, and the server talks to the database in SQL. Your job in this guide is to make all three exist and find each other.

Step 1 — Install Node.js

Node is the thing that runs JavaScript outside a browser. It is to JavaScript what the python command is to Python. You cannot run the server without it.

  1. Go to nodejs.org and download the LTS version.
  2. Run the installer, accept every default.
  3. Restart your terminal afterwards, or the next step won't see it.

Node comes with npm, its package manager — the equivalent of pip in Python or Maven in Java.

Step 2 — Open a terminal and learn four commands

On Mac, open Terminal. On Windows, open PowerShell. The terminal is just a way to run programs by typing their name instead of clicking them. Four commands cover everything you need here:

command what it does
pwdPrints which folder you are currently "standing in".
lsLists the files here. On Windows PowerShell this also works.
cd folderWalk into a folder. cd .. walks back out one level.
Ctrl + CNot a command — the keystroke that stops a running program. You will need this constantly.

Download this project to your computer, unzip it somewhere you can find (Desktop is fine), then in the terminal walk into it. Check you're in the right place:

$ cd Desktop/simfolio
$ ls

You should see docs, server, src and Simfolio.dc.html listed. If you don't, you're in the wrong folder — cd .. and try again.

Step 3 — Install the server's dependencies

The server uses nine libraries other people wrote (a web framework, a password hasher, a database driver). They aren't in the project folder — only their names are, listed in server/package.json. This is the same idea as a requirements.txt. One command downloads them all:

$ cd server
$ npm install

This takes a minute or two and creates a large node_modules folder. Never edit anything inside it, and never commit it to Git. Warnings in yellow are normal; red ERR! lines are not.

Step 4 — Get two free API keys

Real stock prices have to come from somewhere. Two companies give them away for free at low volume, and this project uses one for each job. An API key is just a long password that identifies you to them — treat it like one.

Finnhub
Live prices, company search, company profiles.
finnhub.io/register
Twelve Data
The price history behind the charts.
twelvedata.com

Sign up with an email, confirm it, copy the key from your dashboard. Paste both somewhere temporary — you need them in the next step. If you'd rather skip this for now, leave them blank: the app falls back to simulated prices and everything else still works.

Step 5 — Create your .env file

Secrets never go in code — they go in a file named .env that Git is told to ignore. The project ships a template. Copy it:

$ cp .env.example .env      # Mac
$ copy .env.example .env    # Windows

Open the new server/.env in any text editor and change exactly three lines. Leave everything else alone.

JWT_SECRET=any-long-random-string-you-invent-right-here
FINNHUB_API_KEY=paste-your-finnhub-key
TWELVEDATA_API_KEY=paste-your-twelvedata-key

No quotes, no spaces around the =. JWT_SECRET is the key the server uses to sign login tokens — mash the keyboard for 40 characters. Notice DATABASE_URL is empty: that's deliberate, and it means "use the simple local database". Keep it empty.

Step 6 — What a database actually is

Stop before you run the next command, because this is the part you said you don't know, and it's ten minutes of reading well spent.

A relational database is a set of tables. A table is a spreadsheet with a fixed set of named columns and any number of rows. This project has five of them, and they look roughly like this:

table one row means
usersOne person: email, hashed password, when they signed up.
accountsOne person's cash balance.
holdings"This user owns 12 shares of AAPL at an average cost of $190.44."
transactionsOne buy, sell, or deposit that happened, with a timestamp.
watchlist"This user is following TSLA."

Rows in different tables point at each other by ID — a holdings row stores a user_id rather than repeating the person's email. That pointing is the "relational" part, and it's the same instinct as an object holding a reference to another object in Java.

SQL is the language you use to talk to it. It's small and reads like English. You do not need to write any today, but you should be able to recognise these four:

SELECT * FROM holdings WHERE user_id = 1;   -- read rows
INSERT INTO watchlist (user_id, symbol) VALUES (1, 'TSLA');
UPDATE accounts SET cash_cents = 500000 WHERE id = 1;
DELETE FROM watchlist WHERE symbol = 'TSLA';
Two words in the next step. Migrate means "create the empty tables" — it runs the SQL that defines the shape of the database. Seed means "put some starter rows in", so you have a demo account to log into instead of an empty app. You run migrate once; you can re-run seed any time.

Your database will be a single file at server/data/simfolio.db. That's SQLite — a whole relational database in one file, no separate program to install. It's real SQL, and it is the right choice while you're learning. Postgres (the industrial version, a server of its own) is already supported for later; that's what DATABASE_URL is for.

Step 7 — Build the database

From inside the server folder:

$ npm run migrate
$ npm run seed

Each should print a short list of what it did and then exit back to your prompt. If migrate prints an error mentioning better-sqlite3, step 3 didn't finish — run npm install again and read its output.

Step 8 — Start the server

$ npm run dev

This one does not exit. It prints something like listening on http://localhost:4000 and then sits there. That's correct — it's the server waiting for questions. Leave this terminal tab open and untouched for as long as you're working. Open a second tab for anything else.

Check it's alive: open localhost:4000/health in your browser. You should see a small blob of JSON. That blob is the entire point of this step — it means your server is running and reachable.

Vocabulary: localhost means "this computer". :4000 is the port — one computer can run many servers, and the port number is how you say which one you mean. Nobody else on the internet can reach it yet.

Step 9 — Open the app and log in

Open Simfolio.dc.html. It checks whether a server is answering on port 4000: if yes it uses it, if no it quietly falls back to running everything in the browser. So if your prices and portfolio survive a hard refresh, you're genuinely talking to the server and the database.

Sign up with any email and password. Then walk the whole loop once, deliberately: deposit cash → search a symbol → buy a few shares → check Holdings → check Activity → sell some → refresh the page and confirm nothing was lost.

That last refresh is the real test. If your holdings vanish, the client is in browser-only mode and never reached the server — go back to step 8.

When it breaks — and it will

This is the actual skill. An error message is not a wall; it's a sentence telling you what happened and where. Read the first few lines of a stack trace and ignore the rest — the top is your code, the bottom is libraries. Here are the failures you are most likely to hit:

Message What it means
command not found: npmNode isn't installed, or you didn't restart the terminal after installing it.
EADDRINUSE :4000A server is already running on that port — probably one you started earlier and forgot. Find that tab and press Ctrl+C.
Cannot find module 'express'You're not in the server folder, or npm install didn't complete.
no such table: usersYou skipped npm run migrate.
401 UnauthorizedYour login token is missing or expired. Log out and back in.
429 Too Many RequestsYou hit the free tier's rate limit at Finnhub or Twelve Data. Wait a minute.
Prices show but charts are emptyTwelve Data key is missing or wrong. Quotes and history come from different vendors.

Two habits worth forming now. First: the browser console — right-click the page, Inspect, Console tab. Front-end errors appear there and nowhere else. Its Network tab shows every request the page made to your server and what came back, which answers "is this the client's fault or the server's?" in about five seconds.

Second: look in your database. Download DB Browser for SQLite, open server/data/simfolio.db, and click through the tables after you place a trade. Watching a row appear the moment you press Buy is the fastest way to make databases stop feeling abstract.

After it works

Don't jump to deploying. Do these in order — each one teaches the thing the next one assumes.

01
Break it on purpose. Change a label in the HTML. Change the starting cash in .env. Delete the .db file and re-run migrate and seed. Nothing here is precious, and you learn the shape of a system by poking it.
02
Follow one feature end to end. Pick "buy". Find the button in the HTML, the method it calls, the request that goes out, the route on the server, the use-case class, the SQL. One trace through all six layers is worth a week of tutorials.
03
Run the tests. npm test in the server folder. Read test/portfolio.test.js — it's the most readable file in the project and it documents the trading rules.
04
Learn Git. Then replay the commit history in docs/GIT-WORKFLOW.md so the repo reads like fifteen pieces of real work instead of one dump. For getting hired this matters more than any feature you could add.
05
Then deploy. Server to Render, client to Vercel, and swap SQLite for Postgres — which is one environment variable, because both sit behind the same interface.
Further reading in this project: docs/STACK.md — every tool and why it's here. docs/ARCHITECTURE.md — how the layers fit. docs/API.md — every endpoint. Read STACK first; it's the one that makes the vocabulary click.
